# Authentication, JWT Lifecycle & Token Storage Threat Model

## 1. Token Storage Threat Model & Security Trade-Offs

In a decoupled REST API architecture with static frontend assets, client-side token storage choices involve distinct security trade-offs:

```text
+-------------------+-----------------------------+------------------------------------+
| Storage Option    | Threat Vector / Trade-Off   | Operational Context in REST        |
+-------------------+-----------------------------+------------------------------------+
| localStorage      | Vulnerable to DOM XSS;      | Standard for cross-origin / MPA    |
|                   | Immune to CSRF in REST      | APIs; persists session across tabs |
+-------------------+-----------------------------+------------------------------------+
| sessionStorage    | Scoped to single tab;       | Clears upon tab close; inconvenient|
|                   | Still vulnerable to DOM XSS | for multi-tab study workflows      |
+-------------------+-----------------------------+------------------------------------+
| HttpOnly Cookie   | Immune to DOM XSS access;   | Requires backend cookie endpoints, |
|                   | Introduces CSRF threat      | SameSite policy & proxy alignment  |
+-------------------+-----------------------------+------------------------------------+
| Memory-Only Token | High XSS resistance;        | Lost on page reload/navigation in  |
| (Closure / Var)   | Destroys session on reload  | Vanilla JS MPA (no refresh cookie) |
+-------------------+-----------------------------+------------------------------------+
```

### 1.1 Rationale for `localStorage` in Vanilla JS Multi-Page Architecture
In this project (multi-page Vanilla JS HTML5 architecture without a single-page framework or HttpOnly cookie refresh endpoint):
- Each HTML page navigation (`window.location.href = 'lessons.html'`) creates a brand-new browser execution context, destroying all JavaScript in-memory state.
- Storing tokens exclusively in memory would force the learner to re-authenticate on every page navigation and page refresh.
- Because the backend does NOT implement an HttpOnly refresh-token endpoint, `localStorage` is the selected mechanism for cross-page session persistence.
- **Compensating Controls**:
  1. **Untrusted Client Storage**: `localStorage` is a client-side convenience store and MUST NOT be claimed as "secure storage". Stored values (`access_token`, `user_info`) are untrusted for authorization.
  2. **Zero Known DOM XSS Tolerance**: Untrusted data must never be interpolated into HTML markup (`vanilla-js-dom-security`).
  3. **Credential Logging Prohibition**: Passwords, tokens, and credentials MUST NEVER be logged to `console.log`.
  4. **Content-Security-Policy (CSP)**: Disallowing `'unsafe-inline'` scripts reduces script injection risk.
  5. **Server-Side Token Revocation (`authorization_version` DEC-42)**: Server validates `auth_ver` and `Active` status on every authenticated request.

### 1.2 JWT Lifetime, Client Logout vs Server-Side Revocation Semantics
- **JWT Lifetime**: Tokens have an authoritative 24-hour validity window (`jwt.expiration-ms: 86400000` / 86,400 seconds) generated by `JwtUtil.java`. There is NO refresh-token endpoint. When a token expires after 24 hours, the user must re-authenticate.
- **Client Logout**: The backend REST API does NOT expose a `/logout` revocation endpoint. Frontend logout is strictly **client-side credential cleanup** (`localStorage.removeItem('access_token')`, `localStorage.removeItem('user_info')`, followed by redirect to `login.html`). Frontend code and documentation MUST NOT pretend that client logout invalidates the token on the server.
- **Server-Side Revocation**: Server-side token invalidation is triggered exclusively through `authorization_version` (DEC-42): when an Admin deactivates an account, bans a user, or updates roles, the backend increments `authorization_version`, causing existing tokens to fail with HTTP 401 on their next request.

### 1.3 CORS Policy (Development vs Production Deployment)
- **Development Configuration**: The backend `SecurityConfig.java:99` defaults `app.cors.allowed-origins` to `http://localhost:5500`, `http://127.0.0.1:5500`, `http://localhost:3000`, and `http://127.0.0.1:3000`.
- **Production Deployment Invariant**: Production environments configure allowed origins at deployment time via the `APP_CORS_ALLOWED_ORIGINS` environment variable. The frontend architecture MUST NOT treat development localhost origins as a hardcoded requirement.

### 1.4 User Profile Roles Boundary
- `UserProfileResponse` (`GET /api/v1/users/profile`) contains personal user data (`fullName`, `emailOrPhone`, `avatarUrl`, etc.) but does **NOT** contain `roles`.
- User roles are provided exclusively in `AuthResponse.roles` upon authentication and stored in client-side session state (`authManager`). The frontend profile UI (`profile.html`) and navigation bars must render role badges from the active session state, never by expecting them from `GET /api/v1/users/profile`.

### 1.5 401 Unauthorized vs 403 Forbidden Discrimination
- **HTTP 401 Unauthorized**: Session is expired, invalid, revoked (`auth_ver` mismatch), or account status is not `Active`.
  - Action: Purge local credentials, dispatch `auth:expired`, and redirect to `login.html`.
- **HTTP 403 Forbidden**: User is authenticated with a valid session, but lacks role permissions (e.g. Learner accessing Creator studio) or violates object ownership (e.g. Creator updating another's lesson, Learner updating another's note).
  - Action: **DO NOT purge credentials**. Display a non-destructive notification ("Bạn không có quyền thực hiện thao tác này") and maintain the active session.

## 2. Server-Side Token Invalidation (`authorization_version` DEC-42)

The database maintains an `authorization_version` column on the `ACCOUNT` table:
- When an account's status changes (`Active` $\rightarrow$ `Inactive` / `Banned`) or roles are reassigned by an Admin, the backend increments `authorization_version`.
- The JWT payload contains the version claim: `auth_ver: <version>` (defined as `JwtUtil.CLAIM_AUTH_VER = "auth_ver"`).
- In `JwtAuthenticationFilter`, the backend validates that the token's `auth_ver` matches the current database record (`account.authorization_version`).
- **Client Impact**: The next time a modified user attempts any request, the server immediately returns **HTTP 401 Unauthorized**. The client API layer detects 401, flushes local credentials, and redirects to login.

## 3. Multi-Tab Session Synchronization

When a user logs out in Tab 1, all other open tabs must immediately detect the session termination and avoid making failing requests with invalid credentials:

```javascript
// frontend/js/auth/auth-state.js

window.addEventListener('storage', (event) => {
  if (event.key === 'access_token' && !event.newValue) {
    // Another tab logged out
    window.location.reload();
  }
});
```

## 4. Authentication Request DTO Contracts (`emailOrPhone`)

To prevent field-mapping errors during form handling, frontend forms MUST conform to the exact Spring Boot DTO field names:

### 4.1 Login Contract (`LoginRequest`)
- **Endpoint**: `POST /api/v1/auth/login`
- **Request Body**:
  ```json
  {
    "emailOrPhone": "learner@example.com",
    "password": "mySecurePassword123"
  }
  ```
- **Unified Identifier**: The field name is `emailOrPhone` (NOT `email`). The login form input MUST have `name="emailOrPhone"` so that validation errors (`emailOrPhone: Email or phone is required`) map correctly via `parseFieldErrors()`.

### 4.2 Registration Contract (`RegisterRequest`)
- **Endpoint**: `POST /api/v1/auth/register`
- **Request Body**:
  ```json
  {
    "emailOrPhone": "learner@example.com",
    "password": "mySecurePassword123",
    "fullName": "Nguyễn Văn A"
  }
  ```
- **Validation Constraints**:
  - `emailOrPhone`: Required (`@NotBlank`), max 191 characters.
  - `password`: Required (`@NotBlank`), **between 6 and 100 characters** (`@Size(min = 6, max = 100)`).
  - `fullName`: Required (`@NotBlank`), max 100 characters.
- **Return**: HTTP 201 Created on success.

## 5. Role-Aware Navigation vs Authoritative Authorization

### Strict Architectural Rule
> **Client-stored role metadata is used SOLELY for presentation, navigation display, and UX.**
> **Frontend role checks are NOT security enforcement.**
> **Backend Spring Security (`@PreAuthorize`) is the SOLE AUTHORITATIVE authorization boundary.**

The frontend MUST NEVER rely on client-side role checks for security:
- **Client role check**: Used only to hide/show navigation links (e.g. show `Admin Dashboard` link only if user roles include `'Admin'`).
- **Role Layer Distinction (CRITICAL CONTRACT)**:
  | Layer | Exact Representation | Source of Truth | Notes |
  |:---|:---|:---|:---|
  | **Database Schema** | `Admin`, `Creator`, `Moderator`, `Learner` | `V2__seed_roles.sql`, `Role.java` | Primary key `role_id` (1=Admin, 2=Creator, 3=Moderator, 4=Learner). |
  | **Backend JSON DTO** | `["Admin"]`, `["Creator"]`, `["Moderator"]`, `["Learner"]` | `AuthResponse.roles`, JWT claim `roles` | `AuthServiceImpl` streams `Role::getRoleName`. **No `ROLE_` prefix in JSON!** |
  | **Spring Security** | `ROLE_Admin`, `ROLE_Creator`, `ROLE_Moderator`, `ROLE_Learner` | `CustomUserDetails.java`, `JwtAuthenticationFilter.java` | Spring Security requires `ROLE_` prefix internally for `hasRole()`. |
  | **Frontend Client** | `roles.includes('Admin')`, `hasRole('Admin')` | `stateManager.hasRole('Admin')` | **MUST check `'Admin'`, `'Creator'`, `'Moderator'`, `'Learner'`. NEVER check `'ROLE_ADMIN'`.** |
- If an unauthorized user manipulates JavaScript memory, tampers with `localStorage`, or directly visits `admin-accounts.html`:
  - Every API request made by that page will receive **HTTP 403 Forbidden** from the Spring Boot backend.
  - The API client displays a standardized "Access Denied" error.
